# dawn-pro-audio-fix

给 **MOONDROP Dawn Pro**（水月雨 USB DAC 小尾巴）在 Windows 上用的音频卡死修复工具。

## 它解决什么问题

这个 USB DAC 在两种情况下会出现同一个症状：**设备是连着的、系统里看得到、音量条也不一定是零，但就是不出声**（播放器进度条照走，网易云 / B 站直接卡住）。

1. **接口接触不良** —— Type-C 口松动，设备在系统里反复「掉线 → 回来」，几分钟内几十上百次。掉得够多之后，音频引擎的状态就被拖坏了。
2. **零掉线卡死** —— 设备一直没掉线、电脑也没睡眠，开机跑了十几个小时后，引擎自己卡死。

两种情况都能靠**重启 Windows 音频服务（`Audiosrv`）**立刻恢复 —— 这就是这个工具做的事。

## 两个工具，选一个

| | 用法 | 适合 |
|---|---|---|
| **手动版** `fix-audio.cmd` | 双击 → UAC → 修完自动关 | 你发现没声音了，点一下 |
| **守护版** `audio-guard.ps1` | 装成计划任务后开机自启 | 想让它自动修 |

### 手动版

双击 `fix-audio.cmd` 即可。也可直接跑脚本：

```powershell
powershell -ExecutionPolicy Bypass -File fix-audio.ps1 -CheckOnly   # 只看状态，不改任何东西
powershell -ExecutionPolicy Bypass -File fix-audio.ps1              # 常规修复
powershell -ExecutionPolicy Bypass -File fix-audio.ps1 -Full        # 连 AudioEndpointBuilder 一起按依赖顺序重启
```

### 守护版

安装（需要管理员）：双击 `install-guard.cmd`
卸载：双击 `uninstall-guard.cmd`

只想观察、不真动手：

```powershell
powershell -ExecutionPolicy Bypass -File audio-guard.ps1 -DryRun -RunSeconds 300
```

## 守护怎么判断「该修了」

三个信号，**主判据是静置刷新**，这点很关键：

| | 信号 | 覆盖的故障 |
|---|---|---|
| **主** | **静置刷新** —— 连续 30 分钟没有任何音频流事件（最后一条是「流停止/暂停」，或压根没有） | 长时间不播放，回来后第一次播就没声音 |
| 辅 | **短命流** —— `PlaybackManager` 里流启动后 5 秒内就停止，且 120 秒内出现 5 次 | 播放器建流失败且留下了事件 |
| 补偿 | **掉线恢复** —— 音频端点从「不在场」变回 ACTIVE | 接触不良型故障 |

主判据为什么必须按**时间**、而不是「等播放发生再看有没有失败」：故障那几次里有一类是设备全程在线、日志里**一条音频事件都没有**，引擎就这么静默卡死了。等用户听到没声音，已经晚了。

静置判据的细节：

- 靠 `Microsoft-Windows-Audio/PlaybackManager` 的流状态事件判断有没有在播，**不看 CPU** —— 实测 `audiodg` 空闲时也在吃约 1% 的 CPU，和播放时分不开。
- **静置期间按间隔反复刷**，不是「只刷一次」：距上次刷新满 60 分钟（`-RefreshIntervalMinutes`）且静置满 30 分钟，就会再刷一次。
  > 这条是 v1.1.0 修的 bug。v1.0.0 用一个 `refreshedThisIdle` 标志表示「本轮静置已经刷过」，并且启动时若发现 `audiodg` 刚重建，直接把整轮标记成「已刷」。实测后果：2026-10-21 早上 10:37 守护启动（`audiodg` 于 10:36:54 刚重建），之后一整天没人播放，日志心跳一路是「静置 670 分钟 → 1121 分钟」，**一次都没刷**，用户 18:53 回来第一次播放照样卡死。现在改成记录「上次刷新时刻」，按间隔反复刷 —— 静置期间没人在听，刷多少次都不打扰。
- 启动时回看最近 24 小时的事件，避免「守护刚起来就以为已经静置了 30 分钟」。
- 触发前复查最近 60 秒有没有新音频事件，有就跳过本次。
- 守护自己至少醒着 5 分钟（`-StartupGraceMinutes`）才会做第一次刷新，避免刚启动就抖动。
- 兜底：流状态若持续 12 小时都没收到停止事件，按无流处理，并把静置计时起点重置为当时，免得应用没发停止事件导致永远不复位、或反过来立刻误刷。

> ⚠️ **已知局限**：`PlaybackManager` 的事件里没有任何会话 / 流标识字段（`EventData` 是空的），所以只能维护一个全局的「有没有在播」布尔值。多应用同时播放时，A 停下来可能把状态置成「无流」而 B 还在播，若恰好又满足静置和间隔条件就会误重启一次（打断约 5 秒，播放器多半会自动续播）。v1.1.0 改成按间隔反复刷之后，这种情况不再是「只误伤一次」，而是只要 B 一直播、一直不发事件，理论上每 60 分钟就可能被打断一次。权衡：误重启的代价远小于故障时完全没声音；真要规避就把 `-RefreshIntervalMinutes` 调大，或干脆别用守护版、改双击手动版。

复位分两级，尽量少打扰：

1. 端点**不是** ACTIVE 时，先只重启这一个 USB 设备（`pnputil /restart-device`，影响最小）
2. 端点**已经**是 ACTIVE（引擎层卡死，设备级重启注定无效），或者第 1 级没救回来，才重启 `Audiosrv`

限流：两次复位至少隔 60 秒，一小时内最多 2 次。

## 装计划任务时的一个坑（重要）

用 `Register-ScheduledTask` 装守护时，**必须**显式关掉任务计划的一个默认设置：

```powershell
$settings = New-ScheduledTaskSettingsSet -DontStopOnIdleEnd   # 对应 XML 里的 <StopOnIdleEnd>false</StopOnIdleEnd>
```

默认值是 `StopOnIdleEnd = true`，意思是**计算机一旦结束空闲状态（你一碰鼠标键盘），这个任务就被系统停掉**。

踩过的现场：守护每次启动活不过几秒、日志里什么都不留、看起来像「脚本自己崩了」——其实不是崩，是被调度器杀的。`guard-task.ps1` 里已经加上这个参数了；如果你自己改注册脚本，别忘了它。

## 依赖与前提

- Windows 10 / 11
- 需要管理员权限（重启服务、重启设备都要）
- 脚本按 USB VID/PID `2FC6:F06A` 定位设备 —— **换成别的 USB DAC 需要改这个 ID**

## 日志

- `fix-audio.log` —— 手动版的记录
- `audio-guard.log` —— 守护版的记录（复位、跳过、限流都写在这里）

## 已知局限

- 守护版只在作者这一台笔记本 + 一块 Dawn Pro 上验证过，**没有在其他机器上跑过长期测试**
- 「短命流」信号无法区分正常切歌和真正的建流失败
- 多应用同时播放时，静置判据可能误判（见上文「已知局限」），代价是多重启一次
- 它只处理「设备在线但引擎卡死」，**不解决接触不良本身** —— 那是硬件问题，换线、换口、换接口才是正解
